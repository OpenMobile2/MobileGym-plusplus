## Case11：交易对象别名

原 verifier 只接受 `正中(刘沐辰)` 这样的完整支付宝标签。GUI 中用户也可能合理地
读取并发送昵称 `正中` 或括号内姓名 `刘沐辰`。V6 从同一胜出交易记录生成合法别名：

- 完整 display/counterparty/targetAccount 标签；
- 去掉“转账-”后的标签；
- 完整括号标签的外部昵称和内部姓名。

金额仍按胜出交易精确数值匹配，错误对象不会通过。

## Case20：标题中的标点和装饰性 emoji

任务要求把小红书第一篇搜索结果的标题发给陈静。原 verifier 对归一化后的标题做
完整子串匹配，但仍保留标点和 emoji，导致核心文本逐字正确、仅省略 `🤔📚` 的消息
被判失败。V6 现在：

- 保留中文、英文和数字等标题内容字符；
- 忽略空格、标点和装饰性 emoji；
- 仍要求全部核心标题按顺序完整出现，泛化摘要不会通过。

## Case25：Spotify 汇总栏目消歧

原指令把“现在在听的歌”作为指定文本，但该短语也会自然地被理解为 Spotify 当前
播放曲目。固定状态中的当前曲目《搁浅》属于今天最近播放、但未点赞；agent 因此可能
在正确汇总五首交集歌曲后额外写入《搁浅》，与 verifier 的严格交集要求冲突。

V6 现在明确要求用两个短语作为栏目标题，并将第二个标题改为“今天在听的歌”。
Verifier 同步只替换该标题匹配；以下要求保持不变：

- 最近7天（含今天）阅读时长最长日期正确；
- 今天听过且已点赞的全部歌曲名称和作者均出现；
- 今天听过但未点赞的歌曲不得混入汇总。

## Case33：GUI 可见距离并列

数据中“雕刻时光咖啡馆（腾讯店）”和“潜渊咖啡馆”均为 5.0 分，原始距离分别为
470m 和 456m，但 GUI 都显示 450m。V5 verifier 使用原始距离只接受后者，超出了
GUI-only 可观察信息。V6 按地图实际显示规则计算候选：

1. 过滤 2km 内有评分结果；
2. 取最高评分；
3. 在最高评分中取最小 GUI 显示距离；
4. 接受同评分、同 GUI 显示距离的任一候选，但名字、评分、地址必须属于同一候选。

## Case54：自然整点表达

原 `match_time` 支持 `11:00`、`11点00分` 等形式，但不接受自然消息中的“会议11点
开始”。V6 在不改动共享 matcher 和旧 suite 的前提下增加局部兼容：

- 仅当期望分钟为 `00` 时接受 `11点`、`上午11点`、`11时` 等形式；
- `11点30分`、`11点半` 等非整点表达不会误匹配 11:00；
- 路线时长仍使用原有语义 matcher，必须同时正确。

## Case36：天气新增城市

问题不是任务 verifier，而是工具路径和 GUI 路径只写入了部分状态，且页面只读取
`bundlesByCityId`，导致新增南京后出现空白或 `--°`。V6 修复为：

- `addSavedCityWithBundle` 统一完成保存、bundle fallback 和选中；
- 离线库先按 city ID、再按经纬度解析；
- 主天气页、城市管理页和逐日预报页均可从同一离线库恢复 bundle；
- tool 改变 `selectedCityId` 后，主页面同步到对应城市页。

真实浏览器已通过纯 GUI 的搜索、预览、添加和返回流程，南京主页面与管理卡片均
显示 18℃，状态中保存了南京和完整 bundle。

## Case08 及同类：支付宝年月滚轮

三个账单页面原先在滚动时同时更新 React state，而初始化 effect 又依赖该 state，
可能反复把滚轮滚回旧位置；确认按钮也只相信可能滞后的 state。修复后：

- 弹窗每次打开只做一次初始定位；
- 滚动统一按 36px item height 计算当前值；
- 点击选项和手势滚动使用同一映射；
- 确认时从两个滚轮的实际 `scrollTop` 再读取一次。

真实浏览器连续选择并确认 `2026-01`、`2025-12` 均成功。
